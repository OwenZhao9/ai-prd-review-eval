# AI 审 PRD 评测

用大模型逐条审查 PRD 里的需求，并用一套带标准答案的评测集测量它审得准不准，再根据误判修改审查规则。

## 审查规则

6 条规则，全部来自 NASA Systems Engineering Handbook 附录 C《How to Write a Good Requirement — Checklist》，只收录能在单条需求内判定对错的检查项：

| 规则 | 名称 | 对应 NASA 清单 |
|---|---|---|
| R1 | 歧义措辞 | C.4 Clarity：as appropriate、etc.、and/or、but not limited to |
| R2 | 不可验证 | C.4 Verifiability：fast、easy、user-friendly、robust 等无法测量的词 |
| R3 | 一条多需求 | C.4 Clarity：one thought per requirement statement |
| R4 | 待定项未闭环 | C.3：TBD / TBR 要写明负责人和时间 |
| R5 | 写了实现方式 | C.2 / C.4 Compliance：state WHAT, not HOW |
| R6 | 指代不明 | C.4 Clarity：free from indefinite pronouns |

每条规则写明「判定」和「不算违反」两部分，见 `rules/v1.json`、`rules/v2.json`。

## 评测集

需求全部取自 GitHub 上的公开 PRD：英文 15 份、中文 143 份，只用 MIT、Apache-2.0 等允许使用的开源许可的仓库，每条记录了来源仓库和许可。开发集和留出测试集的中文条目来自不同的 PRD，不共用同一份文档。

| 集合 | 条数 | 其中干净需求 | 用途 |
|---|---|---|---|
| 英文开发集 `data/evalset.jsonl` | 74 | 14 | 分析误判、修改规则 |
| 中文开发集 `data/evalset_zh.jsonl` | 37 | 7 | 分析误判、修改规则 |
| 英文留出测试集 `data/holdout.jsonl` | 32 | 8 | 修改规则之前就标好，只用来对比各版本 |
| 中文留出测试集 `data/holdout_zh.jsonl` | 73 | 21 | 同上 |

每个集合由两部分组成：

- **真实需求**：从 PRD 里抽出来，按规则逐条标注；背景介绍、提问、半截句子和标注有争议的条目直接排除。
- **埋问题**：在干净的真实需求上改出一种已知问题（例如把具体数值换成「待定」、把主语换成「它」），标准答案就是埋进去的那一条。

模型和标准答案不一致时先复核标准答案，改动记录在 `data/adjudication.md`。

## 结果

模型：DeepSeek `deepseek-chat`。每个版本跑 3 次，第 1 次温度 0 用来算准确率，3 次合起来算一致性。

**中英文留出测试集合计（105 条，其中干净需求 29 条）**

| 指标 | v1 | v2 | v3 | v4 |
|---|---|---|---|---|
| 总体 F1 | 0.798 | 0.798 | 0.771 | 0.871 |
| 准确率（报出的问题里真问题占比） | 76% | 83% | 67% | 89% |
| 召回率（真问题被找出的比例） | 84% | 77% | 91% | 85% |
| 干净需求被错报 | 5 / 29 | 2 / 29 | 10 / 29 | 2 / 29 |

| 留出测试集 | v1 F1 | v2 F1 | v3 F1 | v4 F1 |
|---|---|---|---|---|
| 中文（73 条） | 0.810 | 0.759 | 0.752 | 0.857 |
| 英文（32 条） | 0.772 | 0.885 | 0.821 | 0.902 |

各规则的指标和对应的处理动作见健康看板 `dashboard.html`。

## 每一版改了什么

每一版只改规则文字（`rules/v*.json`），提示词不动；修改依据只来自开发集的漏判和误判清单（`results/evalset*/v*/errors.md`），留出测试集只用来打分。

| 版本 | 依据 | 修改 | 留出集上的结果 |
|---|---|---|---|
| v2 | 英文开发集误判 | R3 补上「两个独立句子」「性质不同的两个目标」，「不算」补上同一动作多个输入；R6 只认代词；R5 补代码层面的规定；R2 补「已给出确切内容不算」 | 英文 F1 0.772 → 0.885；中文反而 0.810 → 0.759：规则里只举了英文 and 的例子，中文用顿号、分号串起来的多需求被漏掉 |
| v3 | 中文开发集误判 | 给 R1/R2/R3/R5 补中文写法：「等」「关键操作」、斜杠写法、快速/高效/稳定、顿号分号连接的多需求、「基于 XX 实现」 | 召回率升到 91%，但干净需求被错报从 2 / 29 涨到 10 / 29，F1 不升反降：补得太宽，「支持真实城市和虚拟地点」也被拆成两条、句子里有「支持」就报不可验证 |
| v4 | 中文开发集误报 | 收紧 R1/R2/R3 的「不算」：同一动作的几个对象不拆、意思清楚的斜杠不算歧义、只说「支持某功能」不算不可验证 | 合计 F1 0.871，准确率 89%、召回率 85%，错报回到 2 / 29 |

## 还没解决的

- R3 一条多需求在中文留出集上 F1 0.643，是最弱的一条：「同一动作的几个对象」和「几个可以分别验收的要求」之间的界线，模型和规则都还没划清。
- 三次运行结果一致的比例，中文留出集 74%，比英文的 84% 低。
