# AI 审 PRD 评测

用大模型逐条审查 PRD 里的需求，并用一套带标准答案的评测集测量它审得准不准，再根据误判修改审查规则。

在线试用：<https://ai-prd-review.photogif.workers.dev>（粘贴、上传或导入链接即可审查；点「填入示例 PRD」再点「下一步」「开始审查」可直接看到示例结果）

## 概览

| 审查层 | 审查对象 | 规则来源 | 评测集（开发集 / 留出测试集） | 留出测试集结果 |
|---|---|---|---|---|
| 单句审查 R1–R6 | 一条需求 | NASA 需求编写检查清单 | 111 / 105 条 | v1 → v4：F1 0.789 → 0.860，干净需求被错报 5/28 → 2/28 |
| 文档级审查 D1–D3 | 一个功能的完整段落 | 同上 | 21 / 26 段 | doc_v1 F1 0.833（doc_v2、doc_v3 均更低） |
| 账号与权限模块包 A1–A4 | 登录、密码、登录状态、权限管理段落 | NIST SP 800-63B-4、SP 800-53 | 23 / 40 段 | v1 → v3：F1 0.846 → 0.917 |

- **做法**：需求取自 GitHub 上开源许可的 PRD；标准答案在模型运行之前标好；只按开发集的误判改规则，留出测试集只用来打分；人工抽检 20 条标准答案，一致率 95%。没有变好的版本（v3、v5、doc_v2、doc_v3）照实记录。
- **工具**：审查网页（粘贴 PRD 出结果，误判反馈经复核写成评测用例）、健康看板 `dashboard.html`、一致率计算 `agreement.py`。
- **文档**：需求文档 [docs/PRD.md](docs/PRD.md)；每一版改了什么、依据哪些误判 [CHANGELOG.md](CHANGELOG.md)；审查网页和规则的使用说明 [docs/使用指南.md](docs/使用指南.md)；业务模块审查基准怎么确认 [docs/审查基准确认流程.md](docs/审查基准确认流程.md)。

## 审查规则

6 条规则，全部来自 NASA Systems Engineering Handbook 附录 C《How to Write a Good Requirement — Checklist》，只收录能在单条需求内判定对错的检查项：

| 规则 | 名称 | 对应 NASA 清单 |
|---|---|---|
| R1 | 歧义措辞 | C.4 Clarity：as appropriate、etc.、and/or、but not limited to |
| R2 | 不可验证 | C.4 Verifiability：fast、easy、user-friendly、robust 等无法测量的词 |
| R3 | 一条多需求 | C.4 Clarity：one thought per requirement statement |
| R4 | 待定项未闭环 | C.3：TBD / TBR 要写明负责人和时间 |
| R5 | 写了实现方式 | C.2 / C.4 Compliance：state WHAT, not HOW |
| R6 | 指代不明 | C.4 Clarity：free from indefinite pronouns |

每条规则写明「判定」和「不算违反」两部分，见 `rules/v1.json`、`rules/v2.json`。

## 评测集

需求全部取自 GitHub 上的公开 PRD：英文 15 份、中文 143 份，只用 MIT、Apache-2.0 等允许使用的开源许可的仓库，每条记录了来源仓库和许可。开发集和留出测试集的中文条目来自不同的 PRD，不共用同一份文档。

| 集合 | 条数 | 其中干净需求 | 用途 |
|---|---|---|---|
| 英文开发集 `data/evalset.jsonl` | 74 | 14 | 分析误判、修改规则 |
| 中文开发集 `data/evalset_zh.jsonl` | 37 | 7 | 分析误判、修改规则 |
| 英文留出测试集 `data/holdout.jsonl` | 32 | 8 | 修改规则之前就标好，只用来对比各版本 |
| 中文留出测试集 `data/holdout_zh.jsonl` | 73 | 20 | 同上 |

每个集合由两部分组成：

- **真实需求**：从 PRD 里抽出来，按规则逐条标注；背景介绍、提问、半截句子和标注有争议的条目直接排除。
- **埋问题**：在干净的真实需求上改出一种已知问题（例如把具体数值换成「待定」、把主语换成「它」），标准答案就是埋进去的那一条。

模型和标准答案不一致时先复核标准答案，改动记录在 `data/adjudication.md`。

**人工抽检**：从留出测试集抽 20 条（中文 14、英文 6，覆盖 6 条规则和 5 条干净需求），19 条同意原标注，一致率 95%；不同意的 1 条（Z004「资金不足」未定义）已按抽检意见改为 R1，本文所有数字均为改后重算的结果。抽检页面 `标注抽检.html`。

## 结果

模型：DeepSeek `deepseek-chat`。每个版本跑 3 次，第 1 次温度 0 用来算准确率，3 次合起来算一致性。

**中英文留出测试集合计（105 条，其中干净需求 28 条）**

| 指标 | v1 | v2 | v3 | v4 | v5 |
|---|---|---|---|---|---|
| 总体 F1 | 0.789 | 0.788 | 0.763 | 0.860 | 0.848 |
| 准确率（报出的问题里真问题占比） | 76% | 83% | 67% | 89% | 82% |
| 召回率（真问题被找出的比例） | 82% | 75% | 89% | 83% | 88% |
| 干净需求被错报 | 5 / 28 | 1 / 28 | 9 / 28 | 2 / 28 | 4 / 28 |

| 留出测试集 | v1 F1 | v2 F1 | v3 F1 | v4 F1 | v5 F1 |
|---|---|---|---|---|---|
| 中文（73 条） | 0.797 | 0.746 | 0.742 | 0.843 | 0.833 |
| 英文（32 条） | 0.772 | 0.885 | 0.821 | 0.902 | 0.885 |

**定版用 v4。**

各规则的指标和对应的处理动作见健康看板 `dashboard.html`。

## 每一版改了什么

每一版只改规则文字（`rules/v*.json`），提示词不动；修改依据只来自开发集的漏判和误判清单（`results/evalset*/v*/errors.md`），留出测试集只用来打分。

| 版本 | 依据 | 修改 | 留出集上的结果 |
|---|---|---|---|
| v2 | 英文开发集误判 | R3 补上「两个独立句子」「性质不同的两个目标」，「不算」补上同一动作多个输入；R6 只认代词；R5 补代码层面的规定；R2 补「已给出确切内容不算」 | 英文 F1 0.772 → 0.885；中文反而 0.797 → 0.746：规则里只举了英文 and 的例子，中文用顿号、分号串起来的多需求被漏掉 |
| v3 | 中文开发集误判 | 给 R1/R2/R3/R5 补中文写法：「等」「关键操作」、斜杠写法、快速/高效/稳定、顿号分号连接的多需求、「基于 XX 实现」 | 召回率升到 89%，但干净需求被错报从 1 / 28 涨到 9 / 28，F1 不升反降：补得太宽，「支持真实城市和虚拟地点」也被拆成两条、句子里有「支持」就报不可验证 |
| v4 | 中文开发集误报 | 收紧 R1/R2/R3 的「不算」：同一动作的几个对象不拆、意思清楚的斜杠不算歧义、只说「支持某功能」不算不可验证 | 合计 F1 0.860，准确率 89%、召回率 83%，错报回到 2 / 28 |
| v5 | 中英文开发集 v4 的 R3 漏判和误判 | R3 补「分号隔开、约束对象不同的几项」「一项能力加一个独立的性能或容量目标」；「不算」补「在两种实现里任选一种」「对同一个界面元素的修饰」 | 开发集先变差（英文 0.939 → 0.924，中文 0.933 → 0.923）；留出集 R3 中文 F1 0.643 → 0.722，但合计 F1 0.860 → 0.848，干净需求被错报 2 / 28 → 4 / 28，不采用 |

## 文档级审查：整段功能描述

单句规则查不出「缺了什么」，所以另做了一层，审查对象是 PRD 里一个功能的完整段落，规则 3 条，同样来自 NASA 检查清单：

| 规则 | 名称 | 对应 NASA 清单 |
|---|---|---|
| D1 | 缺验收标准 | C.4 Verifiability：Can the criteria for verification be stated? |
| D2 | 缺异常处理 | C.4 Reliability：error detection, reporting, handling, and recovery |
| D3 | 前后矛盾 | C.4 Consistency：without contradicting themselves |

| 集合 | 条数 | 其中干净段落 |
|---|---|---|
| 文档级开发集 `data/doc_evalset.jsonl` | 20（另有 1 条来自网页反馈，在本文结果之后并入） | 8 |
| 文档级留出测试集 `data/doc_holdout.jsonl` | 26 | 8 |

段落取自上面的中文 PRD，开发集和留出集同样来自不同的 PRD；「埋问题」的做法是在干净段落里删掉验收标准或失败处理，或加一句和原文冲突的话。

**留出测试集结果**

| 指标 | doc_v1 | doc_v2 | doc_v3 |
|---|---|---|---|
| 总体 F1 | 0.833 | 0.800 | 0.694 |
| 准确率 | 71% | 73% | 71% |
| 召回率 | 100% | 88% | 68% |
| 干净段落被错报 | 3 / 8 | 3 / 8 | 2 / 8 |

| 版本 | 依据 | 修改 | 结果 |
|---|---|---|---|
| doc_v2 | 开发集 12 条时的误判 | D1/D2 补「不要求逐项罗列」，D3 补「标题承诺和验收指标对不上」 | 开发集变好，留出集 F1 0.833 → 0.800 |
| doc_v3 | 开发集扩到 20 条后的误判 | D2 改成「只看核心动作的失败有没有写」，D1 补「情况—结果式描述算验收依据」 | 错报减少，但漏判大增，留出集 F1 降到 0.694 |

**定版用 doc_v1。** D3 前后矛盾在三个版本里准确率都是 100%；D1、D2 的分歧不在模型，在于「什么算主要的失败情况」「什么算可检查的结果」本身没有统一口径，在 20 条开发集上调规则只是在模型的严和松之间来回摆。要继续提升，先要让多个标注人按同一份口径标同一批段落、算出彼此的一致率，把口径定下来，再改规则。

## 业务模块包：账号与权限

通用规则只查写法，查不出某个业务模块该有的东西。模块包为一个业务模块单独写一组审查规则，第一个是「账号与权限」：审查对象是 PRD 里讲登录、注册、密码、登录状态和用户权限管理的段落，规则 4 条，依据是美国国家标准与技术研究院（NIST）的数字身份标准 SP 800-63B-4 和安全控制目录 SP 800-53：

| 规则 | 名称 | 依据 |
|---|---|---|
| A1 | 缺失败次数限制 | SP 800-63B-4 §3.2.2：连续认证失败次数必须设上限 |
| A2 | 密码规则违背标准 | SP 800-63B-4 §3.1.1.2：最短 8 位；不得要求混合字符类型；不得强制定期改密码 |
| A3 | 登录状态缺失效时间 | SP 800-63B-4 §2.1.3、§5.2：必须设定明确的重新认证时限 |
| A4 | 账号与权限操作缺日志 | SP 800-53 AC-06(09)：记录特权操作的执行 |

规则文件 `rules/module_account_v*.json`，每条写明「判定」和「不算」。

| 集合 | 段数 | 其中干净段落 | 各规则问题数（A1 / A2 / A3 / A4） |
|---|---|---|---|
| 开发集 `data/module_account_evalset.jsonl` | 23 | 13 | 3 / 3 / 2 / 4 |
| 留出测试集 `data/module_account_holdout.jsonl` | 40 | 20 | 7 / 4 / 5 / 7 |

段落取自 30 份中文开源 PRD，开发集和留出集不共用同一份 PRD；留出集 37 段是原文，3 段是埋问题。标准答案在模型运行之前标好并单独提交；口径拿不准的 12 段没有收录，列在《审查基准确认流程》里。

**留出测试集结果**

| 指标 | module_account_v1 | module_account_v2 | module_account_v3 |
|---|---|---|---|
| 总体 F1 | 0.846 | 0.880 | 0.917 |
| 准确率 | 76% | 81% | 88% |
| 召回率 | 96% | 96% | 96% |
| 干净段落被错报 | 1 / 20 | 1 / 20 | 1 / 20 |
| 三次运行结果一致 | 93% | 85% | 90% |

| 规则 | v1 F1 | v2 F1 | v3 F1 |
|---|---|---|---|
| A1 缺失败次数限制 | 1.000 | 1.000 | 1.000 |
| A2 密码规则违背标准 | 0.889 | 1.000 | 1.000 |
| A3 登录状态缺失效时间 | 0.667 | 0.714 | 0.833 |
| A4 账号与权限操作缺日志 | 0.857 | 0.857 | 0.857 |

| 版本 | 依据 | 修改 | 结果 |
|---|---|---|---|
| v2 | 开发集误判 | A3 只在段落明确描述保持登录方式时适用，「7 天免登录」「滑动过期」算写了失效条件；A4 补上「为角色配置或分配权限」，段内提到可查看操作日志就算有记录 | 开发集 F1 0.741 → 0.880；留出集 F1 0.846 → 0.880，A3 错报 5 → 4 次 |
| v3 | 开发集 v2 误判 | A3 报之前先找段内的时长或有效期字样，找到就不报；A4 判定补「描述可以为不同角色配置操作权限」，「不算」补「可以查看操作日志即视为已记录」 | 开发集 F1 0.880 → 0.957；留出集 F1 0.880 → 0.917，A3 错报 4 → 2 次，三次一致 85% → 90% |

**定版用 module_account_v3。** A3 仍是四条里最弱的一条，留出集 F1 0.833。

审查基准怎么由模块负责人确认、多人标注怎么算一致率、分歧怎么裁决，见 [docs/审查基准确认流程.md](docs/审查基准确认流程.md)；一致率用 `agreement.py` 计算。

## 审查网页

在线版：<https://ai-prd-review.photogif.workers.dev>，部署在 Cloudflare Workers，代码在 `deploy/`，数据存在 Cloudflare D1 数据库。页面按 Stitch 设计稿（`design/stitch/all.html`）实现，宽 768 的窄屏下目录收成顶部下拉。需求文档见 [docs/PRD.md](docs/PRD.md)。

- **导入**：粘贴文字；上传 .docx / .pptx / .pdf / .md / .txt（20 MB 以内，在浏览器里转成文字，原文件不上传）；导入 GitHub、GitLab 文件链接、公开网页和文件直链。飞书、腾讯文档、语雀、Notion、Google 文档的链接不抓取，提示导出后上传；飞书另有授权导入（需要在部署配置里填飞书应用的 `FEISHU_APP_ID`、`FEISHU_APP_SECRET`）。
- **拆分预览**：目录树列出每个段落和拆出的需求条数，可以勾选段落、把跳过的段落改为审查、删改需求。表格行按「表头：值」转写，代码块里的行不算需求，超过 1500 字的段落分组做整段检查。标题或正文含登录、密码、权限等词的段落自动勾选账号与权限检查。
- **审查**：单句 v4、文档级 doc_v1、账号与权限 module_account_v3 三组规则，模型 deepseek-chat。每个访客每天 500 次额度，全站上限由部署变量 `GLOBAL_DAILY` 设置；同样的文字再审直接用本机保存的结果，不调用模型、不扣额度；示例 PRD 不扣额度。失败的条目可以单独重试，额度用完的条目第二天点「审查未完成的条目」接着审。
- **结果**：按段落列出问题、触发词高亮、规则和理由；按规则筛选、只看有问题；同一份 PRD 再审时标出「新出现」「上次也有」，并列出「上次有、这次没有」的问题。每条问题可以生成一句修改建议，点「采用」后替换预览里的文字。
- **导出**：Markdown 或纯文本评审意见（下载或复制）；上传的 .docx 可以导出带批注的 Word，批注作者「AI 审 PRD」。
- **反馈与复核**：「这是误判」「漏了问题」，反馈记录当时的规则版本和模型。「反馈复核」页按状态、类型、规则、单条或整段、规则版本筛选；采纳、驳回和「导出已采纳用例」需要复核口令（Cloudflare 密钥 `REVIEW_KEY`）。导出的 `feedback_cases.jsonl` 放进 `data/` 后运行 `python3 merge_feedback.py` 并入开发集。
- **健康看板**：各审查层的留出集 F1、13 条规则的 F1、版本历史、单次运行与多数表决的对比、多人标注一致率，以及近 30 天的线上指标（只记次数和类别，不记 PRD 内容、文件名、链接和访客地址）。
- **GitHub 合并请求**：页面底部「接入 GitHub」生成工作流配置；合并请求修改 PRD 时，`deploy/github/review-pr.mjs` 只审改动涉及的需求和所在段落，结果作为一条评论发在合并请求下，再次推送时更新这条评论。

格式一致性（F23）：158 份 Markdown PRD 用 pandoc 转成 Word、PPT，再由 Word 用 LibreOffice 转成 PDF，用网页同一份解析和拆分代码拆分后，和直接拆 Markdown 的结果比较（`data/format/`，结果在 `results/format/metrics.json`，差异逐条列在 `results/format/diff.md`）：

| 格式 | 段落标题完全一致 | 需求条目完全一致 | 需求条目一致率 |
|---|---|---|---|
| Word | 154 / 158 | 132 / 158 | 99.5% |
| PPT | 0 / 158 | 1 / 158 | 82.8% |
| PDF | 15 / 158 | 3 / 158 | 35.3% |

修改建议（F18）：改写后用单句 v4 再审，原来的规则不再报出、也没有报出其他规则的比例，英文留出集 19 / 23（82.6%），中文留出集 39 / 49（79.6%）。提示词 `prompts/suggest_v2.md`，评测脚本 `suggest_eval.py`，过程见 CHANGELOG。
