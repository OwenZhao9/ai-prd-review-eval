# AI 审 PRD 需求文档

## 1. 一句话说明

PRD 作者有三种方式把 PRD 交给 AI：粘贴文字、上传文件或导入链接。大模型按带出处的规则逐条检查三件事：

- 单条需求写得清不清楚；
- 功能段落缺不缺验收标准和异常处理；
- 账号与权限段落有没有违背 NIST 标准。

问题会标在原文上，可以导出成评审意见、写回 Word 批注，改完再审时能看到哪些问题已经解决。作者认为审错了可以提交反馈，复核人采纳的反馈会变成评测用例。规则每改一版，都要在固定的留出测试集上打分，分数更高才替换线上版本。审查也能接进 GitHub：PRD 在合并请求里被修改时自动审查。

要解决的问题：

1. 只能粘贴文字，不能上传文件，也不能导入链接（S1）。
2. 大部分 PRD 一次审不完（S2：129 / 158）。
3. 表格行和代码块被错误地拆成需求（S2）。
4. 超长段落被截断，页面没有提示（S2、S3）。
5. 结果不能导出（S3）。
6. 在线版的反馈不能回流到评测集（S3）。
7. 评测过的账号与权限规则没有用上（S4）。
8. 四处审查质量短板：R3、运行稳定性、D1 和 D2、A3（S4、S5）。
9. 审查只能在网页上手动发起。158 份样本 PRD 都放在 GitHub 仓库里，修改 PRD 时没有自动审查（S2）。

## 3. 用户与场景

| 用户 | 什么时候用 | 用它做什么 |
|---|---|---|
| PRD 作者 | 写完 PRD、发起评审之前 | 导入 PRD，按问题修改，改完再审一遍，看问题是否消失 |
| 评审人：开发、测试、设计负责人 | 收到 PRD、开评审会之前 | 导出问题清单，带到评审会上逐条确认 |
| 复核人 | 有待复核的反馈时 | 按规则文字判断反馈是否成立，把采纳的导出成评测用例 |
| 规则负责人、模块负责人 | 新规则或新模块包定版之前 | 按《[审查基准确认流程](审查基准确认流程.md)》确认口径 |
| 维护人 | 换规则版本、换模型、发布网页时 | 跑评测，对比留出集分数，部署 |

## 4. 现状与改动总览

| 环节 | 现在 | 改成 | 需求 |
|---|---|---|---|
| 导入 | 粘贴 Markdown 或纯文本 | 增加上传文件（.docx / .pptx / .pdf / .md / .txt），导入公开网页和 GitHub 文件链接，授权导入飞书文档 | F1–F4 |
| 拆分 | 拆完直接审，看不到拆成了什么 | 先出拆分预览，可以勾选段落、删改条目。表格按表头转写，代码块不算需求，超长段落拆开审 | F5–F9 |
| 规模 | 一次最多 60 项、3 万字 | 按勾选内容审，只受每日额度限制 | F11 |
| 规则 | 单句 v4 + 文档级 doc_v1 | 加上账号与权限模块包 v3，按段落内容自动勾选 | F10 |
| 结果 | 只在页面上显示 | 导出 Markdown 评审意见或复制；给 Word 原文件加批注；改完再审时对比两次结果；每条问题附修改建议 | F13–F18 |
| 反馈 | 在线采纳后只改状态 | 导出已采纳的用例，并入开发集。反馈记录规则版本 | F19、F20 |
| 审查质量 | R3、运行稳定性、D1 和 D2、A3 四处短板 | 每一处都有改进做法和换版门槛 | F25–F28 |
| 接入 | 只有网页 | GitHub 合并请求里自动审查；按数据选出第二个业务模块包 | F29、F30 |
| 指标 | 只记每日调用次数 | 记录导入、审查、导出、反馈各环节的次数，不记内容 | 第 7 节 |

## 5. 功能需求

每条需求都写了「验收」。

### 5.1 导入

**F1 粘贴文字（现有）**

- 文本框接受 Markdown 和纯文本。
- 验收：粘贴示例 PRD 后，拆出的段落和需求条目与现在一致：13 个段落、29 条需求。

**F2 上传文件**

- 支持的格式：Word（.docx）、PowerPoint（.pptx）、PDF（.pdf）、Markdown（.md）、纯文本（.txt）。
- 上传方式：点「上传文件」选择，或把文件拖进输入区。一次传一个文件。
- 文件在浏览器里转成文字，原文件不发送到服务器。原因是审查只需要文字，不传原文件，服务器就不会经手文件本身。
- 单个文件不超过 20 MB。
- 转换完成后，文字填进输入区，用户可以修改，然后进入拆分预览（F9）。上传的 .docx 原文件留在浏览器内存里，导出批注版（F16）时使用。
- 失败处理：

  | 情况 | 页面提示 | 是否调用模型 |
  |---|---|---|
  | .doc、.ppt、.wps，或其他不在上面列表里的格式 | 「不支持这个格式，请另存为 .docx、.pptx 或 .pdf 后上传」 | 否 |
  | 文件超过 20 MB | 「文件超过 20 MB，请删去图片后再上传，或复制文字粘贴」 | 否 |
  | 文件设了打开密码 | 「文件已加密，请解除密码后上传」 | 否 |
  | PDF 没有文字层，例如扫描件 | 「这份 PDF 里没有可提取的文字，请上传原始的 Word 文件」 | 否 |
  | 转换后没有任何文字 | 「没有读到文字，请确认文件内容」 | 否 |
  | 扩展名和实际内容不符 | 按文件实际内容判断；判断不出时提示「不支持这个格式」 | 否 |

- 验收：
  - 示例 PRD 由 Markdown 转换出 Word、PPT、PDF 三个版本。上传后，拆出的段落标题和需求条目符合 F23 对该格式的一致标准。
  - 上表每种失败情况各准备 1 个文件，页面给出对应提示，且没有发生模型调用。
  - 上传过程中，浏览器开发者工具的网络记录里没有原文件的上传请求。

**F3 导入链接**

- 输入区旁边有「导入链接」，粘贴一个网址即可导入。
- 支持的链接：

  | 链接类型 | 处理 |
  |---|---|
  | GitHub 文件链接（`github.com/<用户>/<仓库>/blob/<分支或提交>/<路径>`） | 取这个文件的原始 Markdown |
  | 直接指向 .md、.txt、.docx、.pptx、.pdf 文件的公开链接 | 下载后按 F2 的方式转换 |
  | 不需要登录就能打开的公开网页 | 服务端抓取页面，取出正文，转成带标题层级的文字 |

- 需要登录才能看的在线文档，包括飞书、腾讯文档、语雀、Notion、Google 文档的链接：
  - 不抓取。
  - 提示「这个链接需要登录才能看，请在原平台导出为 Word（.docx）或 PDF 后上传」。
  - 飞书链接额外提示导出路径：在桌面端或网页版打开文档，点右上方「…」>「下载为」，可选 Word、PDF 或 Markdown。来源：飞书帮助中心《下载云文档和文件夹到本地》，2026-11-04 查阅。
- 抓取限制，防止这个功能被用来访问内网或刷流量：
  - 只接受 http 和 https。
  - 不访问本机地址、内网地址和云服务器元数据地址。
  - 响应超过 5 MB，或 10 秒内没有收完，就停止并提示。
  - 只处理 HTML、Markdown、纯文本和 F2 列出的文件类型。
  - 每个访客每天最多导入 30 个链接。
  - 抓到的内容只用于这一次返回，不写进数据库。
- 失败处理：

  | 情况 | 页面提示 |
  |---|---|
  | 打不开：404、超时、对方拒绝 | 「这个链接打不开（附原因），请下载文件后上传」 |
  | 打开的是登录页，或取出的正文不到 200 字 | 「没有读到正文，这个页面可能需要登录，请下载文件后上传」 |
  | 内容类型不在支持范围内 | 「这个链接的内容不是文档」 |
  | 本机地址、内网地址 | 「不支持这个地址」 |

- 验收：
  - 从 `data/sources.json`、`data/zh_sources.json` 里抽 20 个 GitHub 链接导入。导入的文字与该文件在 GitHub 同一提交上的原始内容逐字一致。
  - 飞书、腾讯文档、语雀、Notion、Google 文档的链接各试 1 个：页面给出导出提示，服务端没有发出抓取请求。
  - 本机地址、内网地址各试 1 个：被拒绝，并显示「不支持这个地址」。

**F4 授权导入飞书文档**

- 流程：用户点「从飞书导入」，在飞书授权页同意后粘贴飞书文档链接。服务端调用飞书开放平台的「导出云文档」接口，把这份文档导出成 Word，再按 F2 的 Word 方式转换。
- 依据：飞书开放平台《导出云文档概述》，页面最后更新 2024-10-21，2026-11-04 查阅。
  - 新版文档可以导出为 .docx。
  - 导出分三步：创建导出任务、查询导出结果、下载导出文件。
  - 导出任务结束 10 分钟后，导出的文件会被删除。
- 只读取用户这一次给出的文档。导出的文件转成文字后立即丢弃。用户的飞书授权凭证不保存到这次导入结束之后。
- 失败处理：飞书接口返回失败时，显示飞书给出的错误原因，并提示改用手动导出后上传（F2）。
- 验收：用自己账号下的 1 份飞书文档测试，授权导入的拆分结果与在飞书里手动「下载为 Word」再上传的结果一致。

### 5.2 解析与拆分

**F5 统一的文档结构**

- 所有导入方式先转成同一种结构：带层级的标题、段落、列表项、表格。拆分和审查只处理这一种结构，所以审查规则和评测集不随文件格式变化。
- 各格式的转换方式：

  | 格式 | 标题 | 正文 | 不审的内容 |
  |---|---|---|---|
  | Word | 见下面的标题识别规则 | 段落、项目符号列表、编号列表、表格 | 图片、图形、页眉、页脚、原有批注 |
  | PPT | 每页一个段落，页标题作段落标题；没有标题的页记作「第 N 页」 | 文本框、表格 | 图片、图表、演讲者备注 |
  | PDF | 同 Word 没用标题样式时的规则 | 按阅读顺序提取的文字，去掉每页都重复出现的页眉、页脚和页码 | 图片 |
  | Markdown、纯文本 | `#` 到 `####` 标题（现有规则） | 现有规则 | 代码块（F7） |

- Word 的标题识别规则：
  - 「标题 1」到「标题 4」样式对应 1–4 级标题。
  - 文档没用标题样式时，满足以下全部条件的行算标题：独占一行；以「1.」「1.2」「一、」「（一）」「第 N 章」开头；不超过 30 字。
- Word 文件里有修订记录时，按「接受全部修订」后的内容审，并在预览顶部提示「已按接受全部修订后的内容审查」。
- 不审的图片、图表数量显示在拆分预览顶部：「有 N 张图片未审查」。
- 验收：见 F23 格式一致性评测。

**F6 表格**

- 表格的一行含需求词时，算一条需求。需求词沿用现有词表：
  - 中文：必须、应当、应该、需要、须、支持、允许、可以、能够、不得、禁止；
  - 英文：must、shall、should、will、can、support、allow。
- 发给模型之前，把这一行转写成「表头 1：值 1；表头 2：值 2」，不带竖线。
- 表头行和分隔行不算需求。
- 验收：
  - 158 份样本重新统计，带竖线的需求条目从 495 条降到 0。
  - 抽 20 条转写后的表格行人工核对：表头和值一一对应。

**F7 代码块**

- Markdown 代码块（两行 ``` 之间的内容）里的行不算单条需求，包括 Mermaid 流程图。
- 整段检查仍然把代码块作为段落内容的一部分。
- 验收：158 份样本重新统计，来自代码块的需求条目从 468 条降到 0。

**F8 超长段落**

- 整段检查的段落超过 1500 字时，先按下一级标题拆开。拆完仍超过 1500 字的，按完整的列表项或自然段分组，每组不超过 1500 字，每组各做一次整段检查。
- 依据：整段检查的评测集里，最长的段落是 1537 字（账号与权限开发集），文档级留出集最长 1366 字。分组上限取 1500 字，和评测过的段落长度在同一范围。158 份样本里，超过 1500 字的段落有 71 个，占 3151 个整段检查段落的 2.3%。
- 拆分预览里，这类段落标出「本段 N 字，已分成 M 组整段检查」。
- 跨组的前后矛盾（D3）查不出来。预览里的这条标注同时写明「跨组的前后矛盾不检查」。
- 验收：158 份样本重新拆分，不再有超过 1500 字的整段检查项。

**F9 拆分预览**

- 导入后先显示拆分结果，用户确认后再审。
- 预览内容：
  - 目录树：每个段落的标题、层级、需求条数。被跳过的段落（背景、范围这类）显示为灰色，写明跳过原因，即标题里命中的词。
  - 每个段落可以展开，查看拆出的每一条需求。
  - 顶部数字：功能段落数、需求条数、本次将调用模型的次数、今天剩余的额度。
- 用户可以：
  - 勾选或取消一个段落，取消后这一段不审；
  - 把被跳过的段落改为审查；
  - 删掉一条误拆出来的需求；
  - 修改一条需求的文字。
- 默认所有功能段落都勾选。本次调用次数超过今天剩余额度时，按文档顺序勾选到额度用完为止，并提示「今天的额度只够审前 N 个段落，可以改选要审的段落」。
- 验收：
  - 示例 PRD 的预览里，段落数和需求条数与现在审查结果页的数字一致。
  - 取消一个段落后，「本次将调用模型的次数」减少这一段的项数；审查结果里这一段显示「未勾选，未审查」。

### 5.3 审查

**F10 规则组**

- 单句规则 v4 和文档级规则 doc_v1 对所有勾选的段落运行（现有）。
- 账号与权限模块包 module_account_v3：
  - 段落的标题或正文含以下任一词时，预览里自动勾选这一段的「账号与权限检查」：登录、注册、密码、验证码、免登录、会话、权限、角色、管理员。
  - 用户可以手动改勾选。
- 结果页顶部写明本次用到的规则组、版本和模型名称。
- 网页上的规则与 `rules/` 里的定版一致。规则文件由 `deploy/build.py` 生成（现有）。
- 验收：
  - 把 `data/module_account_holdout.jsonl` 的 40 段拼成一份 PRD 导入，勾选全部段落做账号与权限检查。
  - 网页结果与 `python3 evaluate.py module_account_v3 --set module_account_holdout` 第 1 次运行的结果逐段一致。

**F11 额度**

- 去掉「一次最多 60 项」和「只审前 3 万字」两条限制。一次审多少由拆分预览里的勾选决定。
- 每个访客每天的额度不少于 500 项。这样 158 份样本里最长的一份（479 项）一天内能完整审一遍。
- 全站每天的上限由维护人在部署配置里设置。
- 额度按实际调用模型的次数计算。下面两种情况不计：
  - 缓存命中（F13）；
  - 示例 PRD。
- 审查中途额度用完时：
  - 已完成的结果保留。
  - 没审的条目标「未审查：今天的额度已用完」。
  - 第二天点「审查未完成的条目」，只审这些条目。
- 验收：把额度临时设为 10，审一份 20 项的 PRD。
  - 前 10 项有结果，后 10 项显示额度已用完。
  - 重置额度后点「审查未完成的条目」，只调用 10 次。

**F12 进度与失败重试**

- 审查时显示「已完成 X / 共 Y 项」（现有）和已用时间。
- 模型返回的结果无法解析时，自动重试 1 次（现有）。仍然失败的条目标「审查失败」，并显示原因，例如模型接口返回的状态码。
- 结果页有「重试失败的条目」，只重新调用失败的那些。
- 审查进行中关闭或刷新页面时，浏览器弹出确认。
- 验收：
  - 审查中途断网，失败的条目显示原因。
  - 恢复网络后点「重试失败的条目」，调用次数等于失败的条数。

**F13 结果缓存**

- 每个审查项的结果保存在本机浏览器里，按「文字内容 + 规则版本 + 模型」识别。
- 同样的文字再审时，直接使用保存的结果，不调用模型，不扣额度。
- 规则版本或模型变化后，旧结果不再使用。
- 页面提供「清除本机保存的结果」。清除浏览器数据后缓存也会消失。
- 验收：
  - 同一份 PRD 连续审两次，第二次调用次数为 0。
  - 改动其中 1 条需求后再审，调用次数为 2：这条需求的单句检查 1 次，加上它所在段落的整段检查 1 次。

### 5.4 结果

**F14 结果页**

- 顶部汇总以下数字：
  - 审查的段落数、需求条数、有问题的条数；
  - 每条规则的问题数；
  - 未审查的条数，按原因分开计：未勾选、额度用完、审查失败。
- 筛选：按规则筛选，或只看有问题的条目。
- 左侧是目录，点击可以跳到对应段落，每个段落旁标出问题数。
- 每条问题包含：
  - 原文里高亮的触发词（现有）；
  - 规则编号、规则名称和理由；
  - 「这是误判」按钮。
- 验收：示例 PRD 结果页的各项计数，与逐条结果加起来的数字一致。

**F15 导出评审意见**

- 「导出 Markdown」下载一个 .md 文件。「复制」把同样的内容复制到剪贴板。
- 导出内容：
  - 文件头：PRD 名称（文件名或链接）、审查时间、规则版本、模型。
  - 正文：按段落顺序排列，每条问题一行，依次写段落标题、需求原文、规则编号和名称、理由。
  - 末尾：列出未审查的条目及原因。
- 导出文件在浏览器里生成，不经过服务器。
- 验收：
  - 导出文件里的问题条数等于结果页上的问题数。
  - 用 Markdown 预览打开，表格每行的列数与表头一致。

**F16 Word 批注版**

- 只对上传的 .docx 提供「导出带批注的 Word」。
- 在原文件里每条有问题的需求处插入一条批注：
  - 批注内容：「规则编号 规则名称：理由」；
  - 批注作者：「AI 审 PRD」。
- 正文、格式和原有批注都不改。
- 在原文件里找不到某条需求的位置时（例如转换时合并了段落），批注加在它所在段落的标题上，并在批注里写出这条需求的原文。
- 验收：
  - 示例 PRD 的 Word 版导出后，用 Word 打开，批注数等于问题数。
  - 与原文件比较，除新增的批注外没有其他变化。

**F17 再审对比（依赖 F13）**

- 本机浏览器保存最近 10 次审查结果，只存在本机。
- 同一份 PRD 再审时，结果页这样标注：
  - 每条问题标「新出现」或「上次也有」；
  - 单独列出「上次有、这次没有」的问题。
- 「同一份 PRD」指文件名或链接相同。
- 两次结果按需求原文匹配，改过文字的条目算新条目。
- 验收：
  - 示例 PRD 审一次，然后改掉其中 1 条被报出的问题，再审一次。
  - 这个问题出现在「上次有、这次没有」里，其余问题都标「上次也有」。

**F18 修改建议**

- 每条问题下给出一句改写后的需求。用户点「采用」后，才替换预览里的文字。
- 上线前先做评测：
  1. 用开发集和留出测试集里被报出问题的条目生成改写。
  2. 把改写再审查一遍。
  3. 统计「原来的规则不再报出，也没有报出其他规则」的比例，写进 CHANGELOG。
  4. 改写的提示词只按开发集的结果调整。

### 5.5 反馈与复核

**F19 反馈（现有做法增加两项）**

- 「这是误判」和「漏了问题」保持现有做法。
- 访客可以提交和查看反馈；采纳和驳回需要复核口令（现有）。
- 新增一：提交按钮旁写明「反馈会把这条需求原文保存到服务器，供复核和评测使用」。
- 新增二：每条反馈记录当时的规则版本和模型名称。本机版已经记录了规则版本，在线版补上。原因：规则换版后，旧反馈里「AI 原本报的规则」对应的是旧版本，复核时要知道是哪一版报的。
- 验收：在线版提交 1 条反馈后，数据库里这条记录带有规则版本和模型名称。

**F20 导出已采纳用例**

- 「反馈复核」页增加「导出已采纳用例」。验证复核口令后，下载 `feedback_cases.jsonl`。
- 文件格式与本机版 `app.py` 写出的一致，字段是 id、kind、level、text、labels、source_feedback。labels 的算法也与本机版一致：
  - 误判：AI 原本报的规则去掉被反馈的那一条；
  - 漏判：AI 原本报的规则加上被反馈的那一条。
- 维护人把文件放进 `data/`，运行 `python3 merge_feedback.py` 并入开发集。用例只进开发集，不进留出测试集（现有规则）。同一用例重复导出时，`merge_feedback.py` 按 id 去重（现有）。
- 验收：
  1. 在线版采纳 1 条误判反馈。
  2. 导出文件里有这 1 条，labels 等于 AI 原本报的规则去掉这一条。
  3. 运行 `merge_feedback.py` 后开发集多 1 条；再运行一次，条数不再增加。

**F21 复核页筛选**

- 按以下条件筛选反馈：状态、规则、反馈类型（误判或漏判）、单条或整段、规则版本。
- 验收：每种筛选条件下显示的条数，与数据库里按同样条件查询的条数一致。

### 5.6 评测与发布

**F22 换版门槛（现有做法写成规则）**

- 新规则版本只按开发集的误判修改。
- 同时满足以下两条，才替换网页上的版本：
  - 在留出测试集上，合计 F1 高于当前定版；
  - 干净需求被错报的数量不多于当前定版。
- 不替换的版本也照实写进 CHANGELOG，例如 v5。
- 换模型用同样的门槛：用定版规则在新模型上跑留出测试集，合计 F1 不低于当前模型，干净需求被错报的数量不多于当前模型。
- 标准答案的任何改动都写进 `data/adjudication.md`（现有）。

**F23 格式一致性评测**

- 目的：确认换了文件格式，拆出来的段落和需求不变，这样留出测试集的分数同样适用于 Word、PPT、PDF。
- 做法：
  1. 把 158 份 Markdown PRD 分别转成 Word、PPT、PDF。转换脚本和生成的文件放进 `data/format/`。
  2. 用 F5 的方式解析转出的文件，再拆分。
  3. 和直接用 Markdown 拆出的结果逐条比较。这一步不调用模型。
- 指标，每种格式分别计算：
  - 段落标题完全一致的 PRD 份数；
  - 需求条目完全一致的 PRD 份数；
  - 需求条目一致率，即两边都有的条目数除以 Markdown 拆出的条目数。
- 结果写进 `results/format/metrics.json`，不一致的条目逐条列进 `results/format/diff.md`。
- 上线条件：
  - Word 上传：158 份的需求条目全部一致才上线。
  - PPT、PDF 上传：上线时把一致率写进 README。

**F24 线上指标**

见第 7 节。

### 5.7 审查质量

四处短板用同一套做法：只按开发集的误判修改；新增的标准答案在模型运行之前标好并单独提交；改完在留出测试集上打分，满足 F22 的换版门槛才替换线上版本。

**F25 R3 一条多需求**

- 现状：v4 在中文留出集上 R3 的 F1 是 0.643。v5 只补了规则文字，R3 升到 0.722，但其他规则的误报增加，合计 F1 从 0.860 降到 0.848，没有采用（CHANGELOG）。
- 做法：
  1. 从开发集所用的中文 PRD 里补 R3 的边界用例，「该拆」和「不该拆」成对收录。例如「按联赛、时间筛选」是同一动作的几个对象，不拆；「支持追问和重新分析」是两个可以分别验收的动作，要拆。留出集所用的 PRD 不取。
  2. 按扩充后的开发集误判，只改 R3 的「判定」和「不算」，其他规则不动。
- 验收：中文留出集 R3 的 F1 高于 0.643，且单句审查整体满足 F22。

**F26 运行稳定性**

- 现状：v4 在留出集上连跑 3 次，结果完全相同的比例中文 74%、英文 84%。同一份 PRD 审两次，结果可能不一样。
- 做法：每个审查项调用模型 3 次，至少 2 次报出的问题才算报出（多数表决）。
  1. 先在开发集上比较「单次」和「多数表决」的 F1，再到留出集上打分。
  2. 现有评测每个版本已经跑了 3 次，预测存在 `results/<集合>/<版本>/predictions_run1.jsonl` 到 `predictions_run3.jsonl`，多数表决的 F1 可以直接从这些文件算出，不用重新调用模型。
  3. 稳定性的算法：再跑 3 次组成第二组多数表决，两组结果完全相同的条目比例，就是多数表决的一致率。
- 代价：每个审查项的调用次数变成 3 倍，额度（F11）按实际调用次数扣。
- 验收：多数表决在留出集上满足 F22，且一致率高于单次运行（中文 74%、英文 84%）。两项结果写进 `results/` 和健康看板。

**F27 D1 缺验收标准、D2 缺异常处理的口径**

- 现状：doc_v1 在文档级留出集上 D1 的 F1 是 0.762、D2 是 0.800，干净段落被错报 3 / 8。doc_v2、doc_v3 按开发集改规则后，留出集合计 F1 反而降到 0.800、0.694。README 记录的原因是「什么算主要的失败情况」「什么算可检查的结果」没有统一口径。
- 做法，按《[审查基准确认流程](审查基准确认流程.md)》：
  1. 至少 2 名标注人互不看答案，独立标注文档级开发集的 21 段，只标 D1、D2。
  2. 用 `python3 agreement.py 标注A.jsonl 标注B.jsonl --rules doc_v1` 算每条规则的一致率和 Cohen's kappa（扣除碰巧一致之后的一致程度，1 为完全一致，0 为和随机标注没有区别）。
  3. 规则负责人逐段裁决分歧，把裁决理由补进 D1、D2 的「判定」和「不算」。标准答案的改动写进 `data/adjudication.md`。
  4. 一致率达到规则负责人认可的水平后，再按开发集误判改规则。
- 需要的人：至少 2 名标注人、1 名规则负责人。
- 验收：一致率和 kappa 写进 `results/agreement/doc_v1.json`；改后的规则在文档级留出集上满足 F22，干净段落错报不多于 3 / 8。

**F28 A3 登录状态缺失效时间**

- 现状：module_account_v3 在留出集上 A3 的 F1 是 0.833，错报 2 次，是账号与权限模块里最弱的一条。排除段落里有 2 段的口径和 A3 有关（S5）：
  - 01MVP/blog-starter「登录」：Session Cookie 算不算描述了登录状态保持；
  - yangyunice/WorkMesh「8.3 安全建议」：「Token 管理」算不算描述了登录状态保持。
- 做法：
  1. 模块负责人裁定这 2 段的口径，写进 A3 的「判定」或「不算」。
  2. 这 2 段按裁定结果标好答案，并入账号与权限开发集。它们来自的两份 PRD 都不在留出集里。
  3. 按开发集误判改 A3。
- 验收：A3 在留出集上的 F1 高于 0.833，且模块整体满足 F22。

### 5.8 接入与扩展

**F29 GitHub 合并请求自动审查**

- 依据：158 份样本 PRD 都存放在 GitHub 仓库里，仓库和文件路径记录在 `data/sources.json`、`data/zh_sources.json`。
- 用户在自己的仓库里安装后，配置 PRD 文件的路径，例如 `docs/PRD.md`。
- 合并请求修改了这些文件时，自动审查改动涉及的需求和它们所在的段落，没改的部分不审。
- 结果作为一条评论发在合并请求下，格式与 F15 导出的 Markdown 相同。同一个合并请求再次推送提交时，更新这条评论，不新增评论。
- 模型 API Key 用仓库自己配置的密钥，不经过本项目的服务器，也不占在线版额度。
- 审查失败时，评论里写明失败的条目和原因，不阻止合并。
- 验收：
  - 在测试仓库里用示例 PRD 开一个合并请求，改动其中 2 条需求：评论里只有这 2 条需求和它们所在段落的审查结果。
  - 这些结果与网页对同样文字的审查结果一致。
  - 再推送一次提交后，合并请求下仍然只有 1 条评论，内容已更新。

**F30 第二个业务模块包**

- 选哪个模块，用数据决定：
  1. 统计 158 份样本 PRD 里功能段落标题的主题，算出每个主题出现在多少份 PRD 里。
  2. 加上第 7 节「漏了问题」反馈里，被反馈段落的标题主题。
  3. 只选能找到官方标准作为规则依据的主题。找不到一手依据的主题不做。
- 从规则草案到定版，按《审查基准确认流程》走：负责人确认、多人标注算一致率、分歧裁决。评测集按 PRD 分成开发集和留出集，标准答案在模型运行之前标好。
- 网页接入方式与账号与权限模块相同（F10）：按关键词自动勾选，用户可以改。
- 验收：
  - 主题统计写进 `results/module_topics.json`，选中的模块和理由写进 CHANGELOG。
  - 新模块的留出集 F1 和干净段落错报写进 README 和健康看板。

## 6. 非功能需求

| 类别 | 要求 |
|---|---|
| 隐私 | 上传的文件在浏览器内转换，原文件不离开浏览器。拆好的文字发给模型接口（当前是 DeepSeek）审查。服务器不保存 PRD 原文，只保存三样东西：每日调用计数、访客主动提交的反馈（含那条需求原文）、第 7 节中不含内容的使用计数。现有提示「粘贴的内容会发送给 DeepSeek 模型审查，请不要粘贴涉密内容」保留，上传和链接导入时同样显示。 |
| 密钥 | 模型 API Key 和复核口令只存在 Cloudflare 密钥里，不进仓库，也不发到浏览器（现有）。 |
| 链接抓取 | 见 F3 的抓取限制。 |
| 稳定性 | 单个审查项失败，不影响其他项（现有）。模型接口返回错误时，显示状态码。 |
| 浏览器 | 支持 Chrome、Edge、Safari、Firefox 的当前版本。页面宽度 1280 像素及以上时，目录和结果两栏完整显示；更窄时目录收起。 |
| 可追溯 | 每次审查的结果页和导出文件都带规则版本、模型名称和审查时间。 |
| 本机版与在线版一致 | 本机版 `app.py` 和 Cloudflare 版用同一套拆分规则和同一个定版规则。拆分逻辑只维护一份，由 `deploy/build.py` 生成到两个版本。现在 Python 和 JavaScript 各写了一份。 |

## 7. 指标与埋点

只记次数和类别，不记 PRD 内容、文件名、链接地址和访客地址。数据按天汇总，存进 D1 数据库。

| 指标 | 计算方式 | 数字异常时做什么 |
|---|---|---|
| 导入成功率，按导入方式分：粘贴、各文件格式、各链接类型 | 拆出至少 1 个功能段落的次数 ÷ 开始导入的次数 | 按失败提示的类型（F2、F3 的表格）分别计数，对应修改解析逻辑或提示文字 |
| 预览到审查的转化率 | 点「开始审查」的次数 ÷ 出现拆分预览的次数 | 对照「额度不够」提示的出现次数，判断是不是额度造成的 |
| 审查完成率 | 勾选项全部有结果的审查次数 ÷ 开始审查的次数 | 按未完成原因分别计数：模型接口错误、额度用完、中途关闭页面 |
| 每次审查的项数 | 中位数和最大值 | 对照每日额度设置 |
| 失败项占比 | 审查失败的项数 ÷ 调用的项数 | 按模型接口返回码分别计数 |
| 导出率 | 导出或复制的审查次数 ÷ 完成的审查次数 | 按导出方式（Markdown、复制、Word 批注）分别计数；某种方式长期没人用，就把它从结果页的主按钮挪进「更多」菜单 |
| 反馈率 | 提交过反馈的审查次数 ÷ 完成的审查次数 | 按规则分别计数，反馈多的规则先复核 |
| 采纳率，按规则分 | 采纳数 ÷ 已复核数 | 某条规则的误判反馈被采纳得多，这条规则进入下一轮修改 |
| 额度用完的访客数 | 当天出现「额度已用完」的访客数 | 调整每日额度 |

离线的质量指标沿用现有做法，不新增埋点：

- 留出测试集上各审查层的 F1、准确率、召回率、干净需求被错报数、三次运行一致率，见 `dashboard.html`；
- 格式一致性，见 F23。

## 8. 上线检查

全部需求按各自的「验收」逐条通过后上线。以下几项不通过就不上线：

1. F23：Word 版 158 份的需求条目全部一致。
2. F10：网页对账号与权限留出集的审查结果，与评测脚本一致。
3. F2、F3：每种失败情况的提示逐一走过，且没有发生模型调用。
4. 示例 PRD 的 Markdown 和 Word 两个版本，审查结果相同。
5. F25–F28：规则或审查方式的每一处改动都满足 F22 的换版门槛。没满足的不上线，照实写进 CHANGELOG。
6. F29：在测试仓库里按验收步骤走通。
7. 第 7 节的每个指标在 D1 数据库里都有当天的计数。

## 9. 不做

- 不保存用户的 PRD，不做账号、团队空间和云端审查历史。原因：服务器不保存 PRD 原文（第 6 节隐私）。
- 不审图片、截图、流程图和图表里的内容。
- 不支持 .doc、.ppt、.wps 这类旧格式，也不支持加密文件。
- 不抓取需要登录的链接。飞书文档走授权导入（F4），其他平台导出后上传。
- 不自动修改用户的 PRD。修改建议（F18）要用户点「采用」才生效。
- AI 的结果是评审前的提示，不代替需求评审。
