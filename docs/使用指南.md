# 使用指南

给两类人看：

- **PRD 作者**：把写好的 PRD 交给 AI 审一遍，看哪些需求写得不清楚、哪些功能段落缺了东西，觉得审错了就点反馈。
- **复核人**：处理大家提交的反馈，决定 AI 到底有没有审错。采纳的反馈会变成评测用例，下一轮改规则时用。

AI 只给提示，不替你做决定。每条结果都写明违反了哪条规则、依据原文哪句话、理由是什么，对不对由你判断。

---

## 一、打开审查网页

审查网页由维护人在本机启动（需要 Python 3，项目根目录下有 `.env` 填好模型接口和 Key）：

```bash
python3 app.py
```

然后在浏览器打开 http://localhost:8787 。页面顶部写着当前使用的规则版本，例如「单句规则 v4 · 文档级规则 doc_v1 · 模型 deepseek-chat」。

页面有两个标签：**审查**（PRD 作者用）和**反馈复核**（复核人用，括号里的数字是待复核的反馈条数）。

---

## 二、PRD 作者：审一份 PRD

### 1. 粘贴

把 PRD 的 Markdown 原文粘进输入框，点「开始审查」。想先看看效果，点「填入示例 PRD」，会填入一份开源项目的需求文档。

审查一般需要 10–40 秒，条目越多越久。

### 2. 网页怎么拆你的 PRD

- **按标题拆段**：每个 `#` 到 `####` 标题下的内容算一个段落。
- **跳过非功能段落**：标题里有背景、目标、范围、场景、用户画像、概述、术语、附录、里程碑、排期、待确认、参考、版本记录等词的段落不审。
- **拆出单条需求**：功能段落里的每个列表项，或者含「必须、应当、需要、支持、允许、可以、不得、禁止」等词的句子，算一条需求。太短的（不到 6 个汉字的中文、不到 30 个字符的英文）、超过 300 字的和以冒号结尾的小标题不算。
- **整段检查**：至少有 2 条需求的段落，额外做一次整段检查。
- **上限**：一次最多审 60 项（整段检查和单条需求合计），超出部分显示「未审查（超出 60 项）」；粘贴内容超过 3 万字的部分不审。PRD 很长时，分几次粘贴。

所以 PRD 用 `##` 标题分功能、功能点写成列表，审得最完整。

### 3. 看结果

结果最上面是四个数：功能段落数、有文档级问题的段落数、有问题的需求条数、耗时。

下面按段落列出：

- **整段检查**：这一段有没有缺验收标准、缺异常处理、前后矛盾。没问题时显示「未发现缺验收标准、缺异常处理、前后矛盾」。
- **每条需求**：有问题时，需求原文里会用黄色高亮触发问题的那几个字，下面是规则编号、规则名称和理由；没问题时显示「未发现问题」。
- 显示「审查失败」的条目是调用模型出错，不代表没有问题，可以重新点一次「开始审查」。

### 4. 怎么改

对照下面第四节的规则说明，看理由站不站得住：

- 站得住：改 PRD。例如被报「不可验证」，就把「快速响应」改成「95% 的请求在 200 毫秒内返回」。
- 站不住：点「这是误判」。
- AI 没报、但你知道这里有问题：点「漏了问题」。

## 三、提反馈

反馈是规则变准的唯一来源，花几秒就能提交。

| 情况 | 操作 |
|---|---|
| AI 报的某条问题其实不成立 | 在那条结果下点「这是误判」，直接提交 |
| AI 没报出来的问题 | 点「漏了问题」→ 选规则 → 写一句说明（选填）→「提交」 |

- 每条反馈只针对一条规则。一条需求被报了两条规则、其中一条错了，就只在错的那条下点「这是误判」。
- 「漏了问题」的下拉框只列出这条需求还没被报的规则。
- 说明写清楚你的理由，复核人会看。例如：「段内第 3 行已经写了失败后保留上次状态」。
- 提交后按钮变成「已提交反馈」，反馈进入「反馈复核」页等待处理。

## 四、规则说明

每条规则都有「算」和「不算」两部分，AI 按完全相同的文字判断。完整原文在 `rules/` 文件夹里对应版本的文件。

### 单句审查（v4）：看一条需求写得清不清楚

依据：NASA《系统工程手册》附录 C「怎样写好一条需求」检查清单。

| 规则 | 算违反 | 不算 |
|---|---|---|
| **R1 歧义措辞** | 不同人读会得出不同理解：「等」「如……」后面的列举没写完；「适当」「必要时」「尽量」「若干」；「关键操作」「相关角色」没说清范围；A/B 斜杠写法没说清是都要还是任选其一 | 列举已写全；「支持 A 或 B」表示任选其一；「穿戴/卸下」这类同一开关的两个动作；括号里直接列出、没有「等」字的例子 |
| **R2 不可验证** | 用形容词描述效果，又没给可测量的标准：快速、高效、稳定、友好、便捷、流畅、智能、全面、合理等 | 同一句已给出数值或可检查的条件；已给出确切内容（如完整提示文案）；「不显示任何……」这种能直接检查的否定条件；只说「支持某功能」 |
| **R3 一条多需求** | 一条里有两个以上可以分别验收的要求：两个独立的句子；分号、逗号串起性质不同的目标；并列几个不同动作（「支持追问和重新分析」） | 同一动作作用在几个对象上（「按联赛、时间、置信度筛选」）；同一界面的几个组成部分（「显示提示文案和重载按钮」）；一个动作的必要组成（「输入邮箱和密码登录」） |
| **R4 待定项未闭环** | 有「待定」「TBD」「TODO」「???」，但没写谁负责、什么时候定 | 待定项写了负责人和截止时间 |
| **R5 写了实现方式** | 规定了具体技术（某个数据库、框架、算法、数据结构，或「基于 XX 实现」），而这个选择不是外部约束要求的；也包括函数返回值、异常处理的写法 | 技术约束来自外部且写明原因（如必须兼容已有系统接口）；产品本身就是某个技术的插件 |
| **R6 指代不明** | 主语或关键对象是「它」「这个」「这些」，在这条需求里找不到指的是什么 | 前一个分句里有明确的先行词；「该系统」「本项目」这类名词短语 |

### 文档级审查（doc_v1）：看一个功能段落缺不缺东西

依据：同一份 NASA 检查清单。

| 规则 | 算违反 | 不算 |
|---|---|---|
| **D1 缺验收标准** | 描述了要做的功能，但整段没有任何能判断「做完没有、做对没有」的条件：没有验收标准，也没有明确的数值、输出或状态 | 有验收标准列表，或每个功能点都写了可直接检查的结果 |
| **D2 缺异常处理** | 功能涉及用户输入、网络或外部服务、文件读写、权限或状态变化，但没写出错、为空、超时、无权限、操作失败时怎么办 | 至少写了主要失败情况的处理；功能本身不会失败（如只展示固定文案） |
| **D3 前后矛盾** | 段内两处说法冲突：数值、上限、状态、权限、流程顺序对不上，照其中一处做就违反另一处 | 两处说的是不同条件或不同对象 |

D1、D2 在「什么算主要的失败情况」「什么算可检查的结果」上还没有统一口径，是误报最多的两条。看到这两条的结果时，多对照「不算」判断一下。

### 账号与权限模块包（module_account_v3）

只审查讲登录、注册、密码、登录状态和用户权限管理的段落。依据：NIST（美国国家标准与技术研究院）数字身份标准 SP 800-63B-4 和安全控制目录 SP 800-53。审查网页目前运行上面两组规则，这一组通过评测脚本运行（`python3 evaluate.py module_account_v3 --set module_account_holdout`）。

| 规则 | 算违反 | 不算 |
|---|---|---|
| **A1 缺失败次数限制** | 用户输入密码、验证码或 PIN 登录，但没写连续失败后的限制（锁定、限流、冷却、图形验证码、最多尝试次数） | 微信一键登录、OAuth 等第三方登录；设备或服务之间的固定密钥认证；只写「登录失败提示」不算有限制 |
| **A2 密码规则违背标准** | 要求混合字符类型（包括「至少包含字母和数字」）；强制定期改密码；最短长度低于 8 位 | 只规定长度、字符范围；密码泄露后要求修改 |
| **A3 登录状态缺失效时间** | 明确描述了保持登录的方式（记住我、免登录、自动续期），但没写多久后或什么条件下要重新登录 | 写了任何失效条件，包括「7 天免登录」、可配置的过期阈值；只写登录方式；「会话」指聊天会话 |
| **A4 账号与权限操作缺日志** | 管理员对别人的账号或权限做操作（增删、禁用用户，分配角色，配置权限，重置他人密码），但没要求记录 | 提到可以查看操作日志或审计日志；只有角色权限对照表；用户改自己的账号；管理业务内容 |

## 五、复核人：处理反馈

### 1. 在哪里

点顶部「反馈复核」。每条反馈显示：状态（待复核 / 已采纳 / 已驳回）、时间、是单条需求还是整段、是「认为是误判」还是「认为漏了问题」、涉及的规则、原文和提交人的说明。待复核的下面有「采纳」「驳回」两个按钮。

### 2. 怎么判断

**只按规则文字判断，不按个人写作习惯判断。** 打开第四节对应规则的「算」和「不算」，逐条对：

1. **原文是否落在「算」里**：找到原文里具体是哪几个字符合判定条件。找不到，说明 AI 报错了（误判成立）或者确实没问题（漏判不成立）。
2. **是否被「不算」排除**：「不算」写到的情况优先。例如 A3，原文写了「7 天免登录」，就落在「不算」里。
3. **规则文字能读出两种意思时，不要硬判**：先驳回，把这条原文和你的疑问记下来，交给规则负责人。这说明规则口径需要先统一，按《[审查基准确认流程](审查基准确认流程.md)》走负责人确认和多人标注，不在复核环节临时定口径。
4. **看同一条的其他结果**：采纳后，系统把「AI 原本报的规则」加上或去掉这一条，作为这条原文的标准答案。所以采纳前要确认这条原文上 AI 报的其他规则也是对的；其他规则也有错的，先让提交人对那条也提反馈，一并处理。

| 情况 | 处理 |
|---|---|
| 「这是误判」，原文落在「不算」里，或找不到符合判定的字 | 采纳 |
| 「漏了问题」，原文能指出符合判定的具体字句，且不在「不算」里 | 采纳 |
| 理由是写作偏好（「我觉得这样写也行」），规则文字明确算违反 | 驳回 |
| 规则文字有两种读法 | 驳回，并把原文交给规则负责人 |

### 3. 采纳之后

- 采纳的反馈写成一条评测用例，存进 `data/feedback_cases.jsonl`，页面上的「已采纳并写成评测用例」数字加一。
- 维护人运行 `python3 merge_feedback.py`，把这些用例并进开发集（单条需求进中文开发集，整段进文档级开发集）。**只进开发集，不进留出测试集**：留出测试集是固定的考卷，只用来给每个版本打分，混进去就失去对比意义。
- 下一轮改规则时，这些用例和开发集里的其他误判一起看。改完后在留出测试集上打分，分数和改动写进 [CHANGELOG.md](../CHANGELOG.md)。

例：示例 PRD「4.2 状态刷新」段落写了「刷新失败提示并保留上次状态」，doc_v1 仍报 D2 缺异常处理。复核人对照 D2 的「不算」（已写主要失败情况的处理），采纳为误判，生成用例 `Fea79b46c`，已并入文档级开发集。

## 六、常见问题

**同一份 PRD 审两次，结果不完全一样？**
网页每次用温度 0（让模型尽量给出确定的答案）调用模型，结果大体稳定，但仍会有少量差别。评测时每个版本跑 3 次，3 次结果完全相同的比例在健康看板 `dashboard.html` 里能看到。

**AI 没报问题，是不是就没问题？**
不是。单句规则在留出测试集上能找出 83% 的问题，文档级规则能找出 100% 但误报较多，各规则的数字见 [README](../README.md) 和看板。AI 审查是第一遍筛查，需求评审照常做。

**PRD 内容会发到哪里？**
网页服务只在本机运行，PRD 原文发给 `.env` 里配置的模型接口做审查；Key 只在服务端读取，不会发到浏览器。

**规则什么时候更新？**
攒够一批开发集误判和采纳的反馈后改一版，在留出测试集上打分，比当前定版好才替换。每一版的改动和分数见 [CHANGELOG.md](../CHANGELOG.md)。
