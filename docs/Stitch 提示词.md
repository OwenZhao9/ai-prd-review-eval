# AI 审 PRD：设计和代码

你接手「AI 审 PRD」审查网页：先用 Stitch 画完整设计图，再按设计图和需求文档写代码。

## 一、准备

- 拉代码：`git clone https://github.com/OwenZhao9/ai-prd-review-eval.git`
- 需求文档：`docs/PRD.md`，30 条需求 F1–F30，每条的验收标准就是完成标准。
- 现有线上版：https://ai-prd-review.pages.dev
  - 跑在 Cloudflare Workers 上，用 D1 数据库。
  - 后端：`deploy/src/index.js`，接口有 /api/meta、/api/item、/api/feedback、/api/feedback/resolve。
  - 前端：`deploy/build.py` 根据 `web/index.html` 生成 `deploy/public/index.html`。
  - 规则在 `rules/`，提示词在 `prompts/`。定版：单句 v4，文档级 doc_v1，账号与权限 module_account_v3。
  - 模型：DeepSeek deepseek-chat。
- 仓库里的 `design/` 是旧设计图，不用。

## 二、设计：只在 Stitch 里做

- 在 Chrome 打开 https://stitch.withgoogle.com ，新建一个项目。
- 先发下面第三部分的「0. 统一风格」，再按顺序一条一条发。
- 设计图的生成和修改都在 Stitch 里用提示词完成，不导出到本机改图。
- Stitch 出错就重发那一条。
- 全部画完后，把 Stitch 项目链接交给用户确认，确认后再写代码。

## 三、代码

- 按 Stitch 设计图和 `docs/PRD.md` 把需求全部做完，包括正常、进行中、失败、空、已完成状态和窄屏（宽 768）。不分期。
- F22 换版门槛没有界面。
- F30 先按需求文档用数据选出模块，再做。
- 写代码时直接用 Stitch 导出的页面代码做起点。

## 四、硬性规则

1. 留出测试集只用来打分，不许照着它的错误改规则。标准答案的任何改动都写进 `data/adjudication.md`。评测数字必须能从 `results/` 复算。
2. 仓库里没有 API Key。需要调模型时向用户要，存在本地 `.env`。部署时用 `wrangler secret put LLM_API_KEY` 设置。Key 不许写进代码、日志、提交记录，`.env` 绝不提交。
3. 覆盖或删除已有文件前先问用户。部署到线上、对外发消息，都先问用户。
4. 提交身份：`git -c user.name=owenzhao9 -c user.email=zhaoningup@gmail.com commit ...`。提交说明用中文，不加署名行。每完成一组需求就提交并推送到 main，推送前确认没有 `.env`、Key、简历文件。
5. 界面文字用中文。
6. 每个关键步骤都截图，截图存到 `过程素材/`，接着已有编号往后排；同时在 `过程素材/过程记录.md` 里按时间顺序记下做了什么、遇到什么问题、怎么解决的。

## 五、汇报

- 全部完成后，对照 `docs/PRD.md` 的验收标准逐条自查，补齐缺口后再汇报。
- 汇报只说：做完了哪些、没做哪些以及原因、需要用户决定的事。

## 0. 统一风格（第一条先发）

为一个中文网页工具「AI 审 PRD」设计桌面端界面，宽 1440。产品作用：产品经理把 PRD（产品需求文档）粘贴、上传或用链接导入，工具把文档拆成一条条需求，用大模型按规则逐条审查，标出有问题的需求、给出原因和修改建议，用户可以反馈误判，维护人复核反馈。风格：简洁、专业、浅色，白底加浅灰背景 #f5f6f8，主色深蓝 #1f4fd1，问题标签用浅红底红字，「未发现问题」用浅绿底绿字，圆角 8–12px，细边框，字体用 Noto Sans SC，界面文字全部中文。所有页面共用一个顶栏：左边产品名「AI 审 PRD」，下面一行小字写当前规则版本「单句规则 v4 · 文档级规则 doc_v1 · 账号与权限 module_account_v3 · 模型 deepseek-chat」；顶栏中间三个标签页「审查」「反馈复核」「健康看板」。规则共 13 条：R1 歧义措辞、R2 不可验证、R3 一条多需求、R4 待定项未闭环、R5 写了实现方式、R6 指代不明、D1 缺异常流程、D2 缺验收标准、D3 术语不一致、A1 登录失败处理、A2 密码规则、A3 登录状态时长、A4 权限变更。先画第一个页面：审查页的导入区，三个页签「粘贴文字」「上传文件」「导入链接」，当前在「粘贴文字」，大文本框里已粘贴一段 PRD 开头，文本框下方有「填入示例 PRD」链接和「下一步：拆分预览」主按钮，页面底部一行小字隐私提示「文档内容只发送给审查用的模型，不保存在服务器上」。

## 1. 导入

**1-2 上传完成**：同一页面切到「上传文件」页签。虚线框上传区，支持 .md .docx .pdf .pptx .txt，单个文件不超过 20 MB。已上传「产品需求文档.docx」，显示文件名、大小、「已识别 13 个段落、29 条需求」，右侧「重新上传」，下方主按钮「下一步：拆分预览」。

**1-3 上传失败**：上传区显示红色提示「这个 PDF 是扫描图片，读不出文字。请上传可复制文字的 PDF，或改用 Word / Markdown」，带「重新上传」按钮。

**1-4 上传解析中**：上传区显示文件名和进度条「正在转换为文档结构… 62%」，主按钮置灰。

**1-5 拖动文件**：文件拖到上传区上方时，上传区变成蓝色高亮虚线框，中间写「松开即可上传」。

**1-6 格式不支持**：上传 .doc 文件后显示提示「不支持 .doc 格式，请在 Word 里另存为 .docx 后再上传」。

**1-7 导入链接**：切到「导入链接」页签。输入框里是一个 GitHub 上的 PRD 文件链接，下方说明「支持 GitHub、GitLab、公开网页和文件直链」，获取成功后显示「已获取：33 个段落、91 条需求」和「下一步：拆分预览」。

**1-8 链接获取中**：输入框下方显示加载动画和「正在获取文档…」，按钮置灰。

**1-9 需要登录的链接**：输入了一个飞书文档链接，提示「这个链接需要登录才能打开。可以在飞书里导出为 Word 再上传，或点下面按钮授权导入」，按钮「从飞书导入」。

**1-10 链接打不开**：提示「链接打不开（返回 404），请检查链接是否正确、文档是否公开」。

**1-11 文件直链**：输入的是一个直接指向 .md 文件的链接，识别为「Markdown 文件」，显示段落数和需求条数。

**1-12 从飞书导入**：弹窗，标题「从飞书导入」，说明需要授权读取所选文档、只读不改，按钮「去飞书授权」和「取消」。

**1-13 飞书导出中**：弹窗显示三步进度：创建导出任务 ✓、等待飞书导出 进行中、下载文档 未开始。

**1-14 飞书导入失败**：弹窗显示错误「飞书返回：没有这个文档的读取权限」，附解决办法和「重试」按钮。

## 2. 拆分预览

**2-1 拆分预览**：左侧是文档目录树，每个段落一行，前面有勾选框，标出这段拆出几条需求；部分段落（如「目录」「修订记录」）自动不勾选并标「已跳过」。右侧是所选段落拆出的需求列表，每条一行，可编辑。顶部汇总条：「13 个段落（跳过 5 个）· 29 条需求 · 预计调用模型 35 次」，右上角主按钮「开始审查」。

**2-2 长文档**：一份 25 个段落、167 条需求的长文档。展示三种拆分：超过 1500 字的长段落按小节分组显示；表格每一行转写成一条需求，保留表头；「账号与权限」段落自动勾选了「账号与权限规则组」，带说明标签。

**2-3 额度不够**：顶部黄色提示条「今天剩余额度只够审前 8 个段落，后面的段落会标为未审查」，代码块段落标「代码块，不审查」。

**2-4 PPT**：上传的是 PPT，每页幻灯片作为一个段落，目录里显示「第 1 页」「第 2 页」…

**2-5 Word 有修订**：顶部提示「这份 Word 有未接受的修订，按接受全部修订后的内容审查」。

**2-6 编辑需求和改为审查**：一个被跳过的段落「1. 背景与目标」点了「改为审查」，多出 2 条需求，汇总从 35 次调用变为 38 次；另有一条需求处于编辑状态，带「保存」「取消」。

## 3. 审查进行与结果

**3-1 审查中**：顶部进度条「已审 14 / 35」，下面实时列出已经出结果的需求，每条带规则标签或「未发现问题」，正在审的显示加载动画，右上角「停止」按钮。

**3-2 审查结束·有未完成**：顶部汇总「完成 160 条，失败 3 条，额度用完未审 4 条」，失败的条目标红并带「重试」，未审的标灰。

**3-3 审查结果**：左侧段落目录，每段后面标问题数；右侧是当前段落「4.4 文件操作」的需求列表，有问题的需求下面列出规则标签（如 R1 歧义措辞）、一句话原因、「修改建议」按钮、「这是误判」「漏了问题」两个反馈按钮；顶部汇总「29 条需求，19 个问题」，筛选「只看有问题」开关和按规则筛选下拉，右上角「导出评审意见」「导出带批注的 Word」。

**3-4 筛选和未审查**：同结果页，筛选只看 R2；汇总区另起一行显示「未审查 1 个段落」。

**3-5 展开未发现问题**：关掉「只看有问题」，显示 2 条「未发现问题」的需求，其中一条显示「漏了问题 · 已提交」。

**3-6 反馈·这是误判**：弹窗，显示原需求和被报出的规则，单选误判原因，备注输入框，隐私提示，按钮「提交」。

**3-7 反馈·漏了问题**：弹窗，选择漏掉的规则，填写说明，按钮「提交」。

**3-8 反馈已提交**：结果页上该问题显示「已反馈误判」，右下角提示「反馈已提交，维护人复核后会用于改进规则」。

**3-9 修改建议**：问题下方展开修改建议卡片，左边原文，右边建议改写，改动处高亮，按钮「复制」「采用」。

**3-10 修改建议已采用**：需求文字已替换成改写后的版本，标「已采用，再审后确认」。

**3-11 再审对比**：改了 2 条需求后再审，结果页显示对比：每条「之前 2 个问题 → 现在 0 个」，已解决的问题划线变灰。

**3-12 再审对比·有新出现**：再审后新出现 R1、R2 两个问题，用「新出现」标签标出。

**3-13 账号与权限结果**：「8.1 登录」「8.2 密码」「8.3 权限」段落的结果，出现 A1–A4 规则标签。

**3-14 上传 Word 后**：结果页「导出带批注的 Word」按钮可用；页面底部「清除本机保存的结果」链接。

## 4. 导出

**4-1 导出评审意见**：弹窗，预览按段落整理的评审意见文本（每条：段落、原需求、问题、建议），格式可选 Markdown / 纯文本，按钮「复制」「下载」。

**4-2 已复制**：右下角提示「已复制 19 条评审意见」。

**4-3 带批注的 Word**：模拟 Word 文档页面，右侧批注栏里每条问题是一条批注，挂在对应需求句子上。

**4-4 找不到原位置**：一条批注挂在段落标题上，批注里写「原句在文档里找不到，批注加在所在段落标题上」。

## 5. 反馈复核（维护人用）

**5-1 待复核**：切到「反馈复核」标签页。左侧筛选：状态（待复核 / 已采纳 / 已驳回）、类型（误判 / 漏报）、规则；右侧反馈列表，每条显示原需求、模型结果、用户反馈、提交时间，按钮「采纳」「驳回」。

**5-2 已采纳**：采纳后显示「已写成评测用例」，顶部按钮「导出已采纳用例」。

**5-3 已驳回**：驳回后显示驳回原因。

**5-4 空**：没有反馈时，中间空状态插画和文字「还没有反馈」。

## 6. GitHub 合并请求

**6-1 接入 GitHub**：设置页，填写仓库、PRD 文件路径、模型接口地址、密钥名称，下方显示生成好的配置片段，按钮「复制配置」。

**6-2 合并请求评论**：GitHub 合并请求页面里的一条机器人评论卡片，标题「AI 审 PRD：本次改动 2 条需求，发现 0 个问题」，下面是表格：段落、需求、问题、建议。

**6-3 合并请求评论·有失败**：同一评论卡片，多一行黄色提示「整段检查调用失败，可重新运行」。

## 7. 健康看板

**7-1 健康看板**：切到「健康看板」标签页。顶部 4 张数字卡：单句规则 F1、文档级规则 F1、账号与权限 F1、干净需求被错报率；下面是 13 条规则的 F1 横向条形图；再下面是版本历史表（v1–v5，每版的 F1 和是否采用）。

**7-2 全部指标**：在 7-1 基础上加两块：多人标注一致率表；线上指标 9 项（审查次数、完成率、失败率、平均耗时、误判反馈率、漏报反馈率、采纳率、导出率、再审率）。

**7-3 提示文案一览**：一张页面列出全部提示文案：上传失败、格式不支持、链接打不开、需要登录、额度不够、审查失败、额度用完，每条显示样式和文字。

## 8. 窄屏（宽 768）

**8-1 窄屏·导入**：把 0 号导入页做成 768 宽，页签和按钮自适应。

**8-2 窄屏·拆分预览**：目录树收成顶部下拉，需求列表全宽。

**8-3 窄屏·审查结果**：段落目录收成顶部下拉，问题卡片全宽。

**8-4 窄屏·反馈复核**：筛选收成顶部一行，列表全宽。

**8-5 窄屏·健康看板**：数字卡两列两行，图表全宽。
