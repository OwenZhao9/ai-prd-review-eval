# 审查基准确认流程

审查基准就是「每条规则什么算违反、什么不算」的口径。这一页规定一个业务模块的审查规则从草案到定版要经过哪些人、做哪些事，以「账号与权限」模块包为例。

## 为什么要先定口径

文档级审查迭代了三版（doc_v1 → doc_v3），留出集 F1 从 0.833 降到 0.694。D3 前后矛盾三版准确率都是 100%；D1 缺验收标准、D2 缺异常处理来回摆动，原因不在模型，而在「什么算主要的失败情况」「什么算可检查的结果」没有统一口径：同一段落换一个人标，答案可能就不一样。口径不统一时，按误判改规则只是在模型的严和松之间来回调。

所以模块包先由负责人确认口径、由多人标注验证口径，口径定下来之后再拿模型跑分、改规则。

## 角色

| 角色 | 做什么 |
|---|---|
| 规则起草人（AI 产品经理） | 写规则草案，找一手依据，准备标注样本，跑评测 |
| 模块负责人 | 确认每条规则保留、修改还是删除；裁决标注分歧；在规则版本上签字定版 |
| 标注人（至少 2 人） | 按规则独立标注同一批段落，互相不看对方答案 |

## 流程

### 1. 起草：每条规则都要有一手依据

规则写在 `rules/module_<名称>_v1.json`，每条包含：

- **依据**：标准或规范的原文条款。账号与权限模块用的是 NIST SP 800-63B-4（数字身份认证）和 NIST SP 800-53 AC-06(09)（特权操作日志），原文链接写在规则文件的 `source` 里。找不到一手依据的规则不写。
- **判定**：什么情况算违反。
- **不算**：容易误报的边界情况。

### 2. 负责人确认

负责人逐条看规则，对每条给出「保留 / 修改 / 删除」和理由。重点确认两件事：

- 这条规则在本公司业务里是否成立。例如 A2 依据 NIST 禁止强制混合字符类型，如果公司有合规要求必须保留字符组合规则，A2 就要改或删。
- 「不算」的边界是否符合业务习惯。例如 A4 把「审核作品、配置规则」划为业务内容管理、不要求日志，负责人要确认这一刀切得对不对。

确认结果记在规则文件的版本说明里，规则版本号随之确定。

### 3. 多人标注，算一致率

1. 从该模块的段落里抽一批（账号与权限模块用开发集 23 段），标注人各自独立标注，每段写违反了哪几条规则。
2. 用 `agreement.py` 比对两份标注：

   ```bash
   python3 agreement.py 标注A.jsonl 标注B.jsonl --rules module_account_v1
   ```

   输出每条规则的一致率和 Cohen's kappa（扣除碰巧一致后的一致程度，1 为完全一致，0 为和随机标注没有区别），以及两人答案不同的段落清单。
3. 一致率低的规则说明口径还没写清楚，回到第 2 步改「判定」或「不算」，再标一轮；一致率达到负责人认可的水平后，这条规则才进入模型评测。

### 4. 分歧裁决

两人答案不同的段落，由负责人逐条裁决：

- 是某个人看漏了：按正确答案改，不改规则。
- 是规则文字有两种读法：先改规则文字（补进「判定」或「不算」），再按新口径裁决。
- 负责人也拿不准的：这一段不进评测集，记录在下面的「排除段落」里，等口径明确后再加入。

每次修改标准答案都写进 `data/adjudication.md`（条目、原标注、改为、理由）。

### 5. 定版之后

- 标准答案在模型运行之前定好；模型和标准答案不一致时，先复核答案，确实标错才改，并留痕。
- 改规则只看开发集的误判清单（`results/module_<名称>_evalset/<版本>/errors.md`），留出测试集只用来打分。
- 审查网页里采纳的反馈按复核结论写成新用例，只并入开发集。
